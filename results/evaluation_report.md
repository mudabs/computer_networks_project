## 6. Interpretation

**Best-effort delivery can lose messages and time out.** At 5% loss on A->C, best-effort delivered 52/60 (86.7%) probes, recorded 8 timeouts and completed the whole sequence in only 0 of 3 runs. It is an unacknowledged service: each message is sent once, no layer notices a lost packet, and the only loss signal is a missing echo that expires after the 1 s observation window.

**Stop-and-wait improves completion through acknowledgements and retransmission (ARQ).** Under the same seeded losses the reliable sender completed 3 of 3 runs and delivered 60/60 (100.0%) messages, using 8 retransmissions (one per timed-out best-effort probe). It keeps one message outstanding, waits for that message's ACK and resends on timeout, so a lost DATA packet is repeated until it is acknowledged. No packet needed more than the 3 allowed retransmissions, so there were 0 failures.

**Loss increases retries and elapsed time.** Loss-free reliable runs took 0.017 s on average; the lossy reliable runs needed 8 retransmissions in total and took 2.02-4.02 s longer per run. Each retransmission cost about 1.01 s of extra elapsed time, which tracks the 1 s retransmission timeout: a lost packet is only detected when the sender's timer expires, so every loss adds one full timeout of idle waiting.

**Reliability has a time and traffic cost.** A loss-free reliable transfer sent 21.0 source packets (20 DATA plus one FIN) and 168.0 link transmissions over all hops including the ACKs; best-effort sends each of the 20 messages once by design. The destination sent 21 ACKs in every run (one per message plus one for the FIN). Under loss the traffic cost was small: exactly one extra link transmission per retransmission (the lost copy never reaches the next hop, so only the resend adds traffic), 1.2-2.4% of the loss-free total. The time cost was far larger, because stop-and-wait idles for a timeout on every loss: throughput fell from 1183 messages/s loss-free to 5.0-9.8 messages/s with loss.

**Timeouts dominate elapsed time in both modes.** At 5% loss a best-effort run took 2.03-4.05 s and a reliable run 2.04-4.04 s: both spend roughly one 1 s timeout per lost packet. The difference is what that time buys: best-effort pays it and still misses the message, reliable pays it and recovers.

**Without loss the two modes behave alike.** At 0% loss best-effort delivered 60/60 (100.0%) and reliable 60/60 (100.0%); reliable mode took 0.8 ms per message against 0.7 ms for best-effort, the small cost of waiting for an ACK before sending the next message.

**Added delay increases round-trip and elapsed time (best-effort baseline only).** Raising the delay on A->C from 0 to 40 ms: at 0% loss the mean time per probe rose from 0.7 to 47.7 ms (about 47.0 ms more per matched probe once timeout waits are removed, against 40 ms configured); at 5% loss the mean time per probe rose from 135.1 to 175.8 ms (about 47.0 ms more per matched probe once timeout waits are removed, against 40 ms configured). Delivery counts were identical for every seed at both delays, so delay changed timing but not which packets were lost. The delay applies to one direction of one link, so a probe pays it once on the way to the destination, not on the returning echo; the difference from the configured value reflects measurement and scheduling overhead, which this data does not isolate. Because reliable mode was not run with added delay, the effect of delay on retransmission behaviour (for example a delay approaching the retransmission timeout causing spurious retransmissions) is not measured here.

**Limits.** Three seeds, one 20-message workload and a single impaired link are small samples; the results show the mechanisms, not population statistics. Best-effort "delivered" counts matched round-trip probes, whereas reliable "delivered" counts DATA accepted by the receiver; with loss only on the forward direction of the impaired link the two coincide here.
